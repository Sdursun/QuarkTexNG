# Phase 3: command buffer over uaenative.library

Status: implemented, 2026-10-04. QuarkTex now runs in 32-bit and 64-bit WinUAE,
and the reference tests match the 0.53 frames in both. The command buffer adds
little speed: a test run takes 4.6 % less wall-clock time in 32-bit WinUAE and
7.5 % less in 64-bit WinUAE (see [Results](#results)).

## Decision

Phase 3 changes only the transport between the 68k libraries and the host. What
gets rendered stays the same; the reference tests prove it.

- The host is reached through `uaenative.library` instead of the uaelib traps
  100-105. The old traps are compiled only into 32-bit WinUAE; the
  `spikes/uaenative` probe shows that the new route works in both builds.
- The 68k side can no longer call `opengl32.dll` directly: in a 64-bit process
  the function pointers do not fit in a 68k register. All OpenGL calls now run in
  the host library.
- Every OpenGL call is written to a command buffer. Calls that take only scalar
  arguments and return nothing stay in the buffer until the next flush.
- Calls that take pointers or return a value flush the buffer at once (they are
  synchronous). They behave exactly as before.
- Warp3D keeps translating to OpenGL on the 68k side. Moving that logic to the
  host is phase 4.

## Why pointer calls stay synchronous

agl.library converts caller memory in place around each call:

```c
void glVertex3fv(GLfloat *v __asm("a0")) {
	SWAP32(v, 3);
	_glVertex3fv(memoffset + (long) v);
	SWAP32(v, 3);
}
```

If such a call were queued, the host would read the data after it had been
swapped back. Running these calls at once keeps the old behaviour, at the cost
of one host call each.

The 336 functions in `gl/glFuncs.txt` split as follows:
- 175 are queued.
- 161 are synchronous: 153 take pointers, 8 return a value, and `glFinish` and
  `glFlush` wait for the host anyway.

The Warp3D drawing path is all scalars: `glBegin`, `glTexCoord4f`, `glColor4f`,
`glVertex3f` and `glEnd`. It is therefore queued completely.

## Components

```
Warp3D.library / agl.library (68k, unchanged except memoffset = 0)
        │  _glXxx(...)               gl/glencode.auto.c, generated
        ▼
gl/gl.c (68k)       append to the buffer; flush when full, on synchronous
        │           calls and before every context call
        │  uaenative.library call_function
        ▼
quarktex-windows-x86[-64].dll (host)
        qt_execute(buffer, length)   host/gldecode.cpp + gldecode.auto.inc
        qt_create_context, qt_move_window, qt_free_context,
        qt_swap_buffers, qt_log, qt_protocol_version
```

### Buffer format

Each command is one header word, `opcode << 16 | word count`, followed by one
32-bit big-endian word per argument. A double takes two words, high word first.
Pointers are Amiga addresses; the host resolves them with `uni_resolve()`, and
address 0 becomes NULL. Opcodes are the line numbers in `glFuncs.txt`, so new
functions are appended at the end. A synchronous call is written like any other
command and flushed right away. `qt_execute` returns the result of the last
command.

Because arguments travel in the buffer and not in registers, there is no
12-register limit. `glMap2d` needs 15 words; 0.53 dropped it silently, and now it
works.

### 68k side (`gl/gl.c`)

- `glInit` opens `uaenative.library` and the host library `quarktex`, checks
  `qt_protocol_version`, and allocates the 256 KB buffer. If any of that fails,
  `W3D_CreateContext` returns `W3D_NODRIVER`. Before, a missing DLL ended in a
  call to address 0.
- `memoffset` stays 0. The existing `memoffset + (long) ptr` expressions then
  pass plain Amiga addresses, so no call sites had to change.

### Host side

- Built from one source as `quarktex-windows-x86.dll` and
  `quarktex-windows-x86-64.dll`. It is installed into the WinUAE directory or
  `plugins/`; `QuarkTex.alib` is no longer used.
- The dispatch in `host/gldecode.auto.inc` is generated by `gl/glgen.cpp` from
  the same `glFuncs.txt` as the 68k encoders.
- Eleven functions are written by hand in `host/gldecode.cpp`:
  - `glGetPointerv` would return 64-bit host pointers. It returns the Amiga
    address passed to the matching `gl*Pointer`, `glInterleavedArrays`,
    `glFeedbackBuffer` or `glSelectBuffer` call instead, so those eight calls
    are hand-written too and record that address.
  - `glGetString` returns 0; agl.library answers it on the 68k side.
- The OpenGL window is a child of the WinUAE display window. The library finds
  that window itself (class `AmigaPowah`), because `uaenative.library` does not
  pass it.

## Tests

- `./build.sh unittest` builds the generated encoder and decoder into one host
  program. Every function goes through encoder, big-endian buffer and decoder
  into a recording stub, and is then called on the stub directly; both
  recordings must match. 325 functions are checked; the 11 hand-written ones are
  left out. Swapping the two words of a double makes 29 checks fail, so the test
  catches such errors.
- `pwsh tests/run.ps1` runs the reference tests in `winuae.exe`;
  `-Emulator winuae64.exe` runs the current build in 64-bit WinUAE and compares
  it with the last 0.53 run. The 0.53 libraries always run in `winuae.exe` with
  the legacy `QuarkTex.alib` from the end of phase 2.
- `t09_throughput` draws 20000 gouraud-shaded triangles per frame and logs
  triangles per second.

## Results

WinUAE 6.0.3, AmigaOS 3.2, 68040 without JIT, `cpu_speed=max`; t09 built with
400000 triangles per frame (1.2 million in all). The E clock measures emulated
time, so the wall-clock time of the whole run, boot included, is given as well.

| Build | Emulator | t09 (E clock) | Whole run (wall clock) |
| --- | --- | --- | --- |
| 0.53, uaelib traps | winuae.exe | 166813 triangles/s | 17.4 s |
| phase 3, command buffer | winuae.exe | 164469 triangles/s | 16.6 s |
| phase 3, command buffer | winuae64.exe | 182578 triangles/s | 16.1 s |

The buffer removes the traps but hardly any time. Inside the emulator a trap is
a plain function call into the host, so the traps were cheap. Most of the cost
is the emulated 68k code: Warp3D's `drawVertex`, the eleven `_gl*` calls per
triangle, and agl.library's byte swapping. That cost only goes down if the work
moves to the host. Phase 4 does that: a triangle becomes one command instead of
eleven.

## Open questions

- Does any application rely on GL errors appearing at the exact call? Queued
  calls report errors at the next flush. QuarkTex only logs errors at swap, so
  this should not matter.
- agl.library's `glArrayElement` asks `_glIsEnabled` six times per vertex, and
  each of those calls is synchronous. Caching the enable state on the 68k
  side would batch that path as well.
- The libraries keep one buffer and are not reentrant, as in 0.53: two tasks
  drawing at the same time would mix their commands.
